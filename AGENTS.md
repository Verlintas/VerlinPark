## Current milestone

**M2 four-tier delegation.** The single-Leader runtime, worktree, approvals, diff, commit/discard, token budgets, cancellation, and persisted plan exist. The Leader submits a validated TeamPlan (departments, Manager titles, profiles, task DAG), then delegates through Manager → Worker → Labour using `delegate`; users can also queue standalone project tasks in the Task Inbox, and the default-on dispatcher turns each into a validated one-task plan with dependency gates and retry reconciliation; plan Manager titles are enforced. Managers must receive a department `title` from the Leader and are read-only by tool policy; Workers get isolated task worktrees, Labour inherits the Worker worktree, and successful Worker commits enter a persisted merge queue and are serially integrated into the session branch. Session diffs are based on the stored base commit. Managers can run up to the configured Worker cap (max 10) in parallel via `delegate_many`; manual parallel tasks must declare non-overlapping write scopes, and final changed paths are checked before serial integration. Structural roles and domain profiles (coding/research/verification/generic) are separate; research has a public-URL `fetch_url` tool. A Verifier must submit an approving verdict before a Worker branch is merged; it has no write/edit tools, and runs in an isolated detached clone of the exact Worker commit, so shell writes/commits/untracked files cannot mutate the Worker worktree or branch; the post-run tracked-file guard remains as defense-in-depth. A Leader or Manager can also delegate a focused task to a configured external Agent Client Protocol (ACP) agent via `delegate_acp`; the external agent is recorded as a Worker; stdio agents run in their own task worktree under the same Seatbelt write sandbox with a scratch HOME, while remote Streamable HTTP/WebSocket agents are trusted external services and are not locally sandboxed, route their permission requests through the risk-based approval policy, receive configured stdio MCP servers, plus HTTP/SSE MCP servers when the agent advertises those MCP transports, in `session/new`, and a stdio agent's `end_turn` commit enters the normal Verifier and merge queue. ACP agents can run over stdio or explicit Streamable HTTP/WebSocket remote transport. Stdio agents remain trusted user binaries; remote agents are trusted external services, and neither transport is a network/credential sandbox. Remote delegation requires `allow_remote` and is approval-classified; it cannot claim local worktree confinement. The Leader can convene a bounded 1–3 round Manager roundtable via `deliberate_team_plan` (all planned Managers, read-only, peer positions shared between rounds), then auto-dispatch the plan in dependency batches via `run_team_plan`; Managers are deterministic department owners in this path, Workers are real agents with task worktrees and Verifier gates, and defaults are 4 Managers / 6 Workers / 12 Labour, runtime caps 5/10/40; plans support up to 100 tasks and Manager creation is lazy. Plan auto-dispatch selects batches with non-overlapping write scopes and uses active Worker slots; task batches respect the configured Worker capacity. The session token budget uses pre-flight reservations, dynamic output limits, and provider-usage settlement; local endpoints without usage report a persisted estimate. A running session can be cooperatively paused at turn/tool boundaries via `session.pause` / `session.resume` (CLI `vp pause` / `vp resume`); the same run continues on resume, and terminal status cannot be overwritten. An operator can also steer a running Leader or Worker through `session.steer` / `vp steer`; steering is persisted, event-backed, addressed to one agent (optionally one plan task), delivered as a labeled user turn immediately before the next provider call, and cancelled if the run ends first. It is operator-only and cooperative: it cannot interrupt an in-flight provider stream or tool call and does not create an agent-to-agent steering tool. A Leader or Manager can also call the read-only `scout` tool for fresh-context exploration; Scout has a read-only tool bundle, no shell/write/merge/worktree, a per-run cap of 3, accounts against Worker capacity and the shared budget, and a post-run worktree-change guard. Shell commands run under a macOS Seatbelt write sandbox confined to the agent worktree, its Git metadata, and a per-agent runtime scratch directory, with an allowlisted environment that excludes provider/daemon secrets, read-denials for common credential/state paths, process-group cleanup on timeout/cancel, and a per-project `ShellPolicy` that can deny network or add read-denials (it can only narrow, never widen); arbitrary reads, network access under `allow`, and daemon-mediated writes are not confined. Tool approvals are risk-based: `smart` (default) allows routine workspace edits, builds, and tests while asking before host-level changes; `strict` asks before every write/shell/external tool; `unattended` never blocks and denies host-level operations. The SwiftUI Settings → General surface and `VERLINPARK_APPROVAL_MODE` select the mode, and approval records persist risk and reason. A project can add bounded `ApprovalTemplate`s (tool/path scoped, External/WorkspaceWrite only, use/expiry capped), identical pending approvals deduplicate and resolve together, and `attention policy` orders/expires/coalesces pending rows; templates can never auto-approve Destructive, HostState, remote, MCP, sensitive GUI, or unknown-risk requests, and deny always wins. Verifier-approved commits enter a persisted session merge queue and a **deterministic Integrator** merges with `--no-ff`, runs `git diff --check`, and optionally runs `VERLINPARK_INTEGRATION_COMMAND` under the same write sandbox and environment allowlist; failed checks roll back to the pre-merge commit, and conflicts abort without changing the session branch. Conflict/failed entries can be retried after rebasing the Worker branch (`merge_queue.retry`, `vp retry`); a conflict can be resolved by an explicit resolver agent (`merge_queue.resolve`, `vp resolve`) that fixes the rebase in the Worker worktree, is re-verified, and then re-enters the deterministic Integrator. A project-level `IntegrationPolicy` can opt into automatic resolution on session idle, with persisted attempt caps and an optional per-resolution token cap; it is off by default. A daemon-wide session admission gate (`VERLINPARK_GLOBAL_SESSION_CAP`, default 4) queues excess session runs as `queued` and admits higher-priority sessions first (session priority -100..100, set at creation or updated with event-backed `session.priority.set`; aging adds one point per `VERLINPARK_PRIORITY_AGING_SECS`, default 60, capped at +100; equal effective priorities round-robin across sessions/projects); cross-session Worker/Labour write scopes wait on a SQLite-backed global write-lease registry (same-session workers share; overlapping scopes in different sessions wait; recovery clears stale leases); plan-task rows are persisted per session/plan revision with priority, dependencies, attempts, and status, rebuilt from plan lifecycle events, exposed through `task.queue` / `vp tasks` and Manage Dash, and can be skipped or retried while the session is not active (`task.skip` / `task.retry`, `vp task-skip` / `task-retry`) or cooperatively cancelled/paused/resumed while running (`task.cancel` / `task.pause` / `task.resume`, task status transitions checked at Worker turn/tool boundaries), all event-backed and replayable; a project-level scheduler policy (persisted `TaskSchedulerPolicy`, **default on** for new projects, cooldown 1–86400s, RPC/CLI/Manage Dash) makes the scheduler pick idle/failed/cancelled sessions with pending tasks by effective priority, aging, and session round-robin before calling `resume_plan`, or, when the policy sets `dispatch_tasks`, calling `dispatch_next_task` to run one ready task per tick and then return the session to idle; the same tick also dispatches project-scoped standalone **task-inbox** items (`intake_tasks`, `intake.list/create/update/dispatch/cancel/retry/delete`, `vp intake*`) by atomically claiming a row, synthesizing and validating a one-task TeamPlan, creating a normal session/worktree, and running the same Worker → Verifier → Integrator path, with intake-to-intake dependency gates, per-project `include_intake` / `max_intake_parallel` (default 2, range 1–10), attempt caps, orchestration backoff, startup/tick reconciliation, manifest/`db-rebuild` persistence, and read-only `scheduler.status` / `vp scheduler` / Manage Dash occupancy; a project row or `VERLINPARK_TASK_SCHEDULER=0` can disable it, and manual Run now overrides the toggle/cap but not dependencies, budgets, capacity, write leases, or verification; and a daemon-wide Worker/Labour capacity controller (`VERLINPARK_GLOBAL_WORKERS` default 12, `VERLINPARK_GLOBAL_LABOUR` default 24) is an additional per-run ceiling that survives provider reconfiguration, is priority-aware with plan task priority, aging, and a session round-robin tie-break, is exposed through `agent.info`, and can opt into budget-gated plan Worker expansion up to the hard cap of 10. Projects also have a deterministic `OrchestrationPolicy` (auto retry, max attempts, exponential backoff, retry priority boost, dependency-failure block/cancel/retry, escalation, automatic blocker resolution). The controller writes `orchestration.decision` and applies retry/block/unblock/cancel/escalate/resolve actions from task completion and a daemon tick; retries use persisted `plan_tasks.next_attempt_at`, are suppressed when the session budget is exhausted, and can be previewed with `orchestration.preview` (`vp orchestrate --dry-run`). `orchestration.overview` provides cross-session Mission Control. Coordination notes and orchestration decisions are persisted SQLite projections rebuilt by replay/repair and bundle import; targeted notes are delivered to the agent mailbox, and plan Workers receive task-specific plus shared coordination briefs. The stored plan supports revision inspection (`team_plan.revision`), restore (`team_plan.restore`), and one-task edit (`team_plan.task_edit`) with active/completed task protection and optimistic expected-revision checks. Session runs and plan resumes hold a durable `runtime_leases` row with heartbeat and TTL (TTL/3 renewal), exposed through `runtime.leases` / `vp leases` and Manage Dash; the data-dir instance lock remains, so this is not a distributed lock service. A `plan_task_progress` companion table records turn/tool progress for task-scoped runs, and the daemon emits thresholded `orchestration.stall` observations (`VERLINPARK_TASK_STALL_SECS`, default 1800, 0 disables) exposed through `session.stalls` / `vp task-stalls`, `task_detail`, `task.queue`, and orchestration snapshots. Observation-only remains the default. A project `OrchestrationPolicy` can opt into `stall_recovery = escalate` or `retry`; retry persists an event-backed recovery intent, requests cooperative cancellation, waits for the task and session to become quiescent, then reuses `retry_plan_task` + `resume_plan` under `stall_min_observations`, `stall_max_attempts`, `stall_grace_secs`, and budget guards. It is same-task/department recovery, not immutable same-agent identity, and failure escalates instead of looping. Operators can also create deferred session continuations with `session.defer` / `vp defer`: a persisted, event-backed row wakes on watched plan tasks settling (`all`/`any`) or a deadline, waits until the session is idle/failed/cancelled, then starts through the normal prompt path. A continuation claims `delivering` before start and fails closed if the daemon restarts mid-delivery; it does not create plan tasks or bypass any gate. An opt-in interval series can repeat after each successful delivery (`session.defer` `every_secs`/`max_runs`): the next deadline-only child is created in the same delivery transaction, is delivery-relative rather than cron, and stops at the run cap or any failure. Prompt, defer, and steer accept an optional `operation_id` backed by `session_operations` receipts; the same id and payload replays, a pending id is in-progress, a different payload conflicts, and a daemon restart turns lingering pending rows into `unknown` so retries fail closed. ## Invariants

1. The Rust daemon owns state; the SwiftUI app is a client.
2. Every session-scoped state change is an event; append events before updating projections. Project/policy/config changes are persisted in SQLite and the project manifest, not yet in a project event stream. Session status, usage, agent status, team plan, todos, messages, merge queue, coordination notes, orchestration decisions, and recovery now use atomic event+projection transactions. `session.replay` checks critical projection drift including the session usage ledger, mailbox, artifact, approval, memory, question, coordination, decision, and task-DAG queue projections, `session.replay {repair:true}` / `vp replay --repair` repairs covered projections, `session.replay {rebuild:true}` / `vp replay --rebuild` forces a rebuild, `session.log_status` / `vp log-status` compares the JSONL mirror with the event table, and `session.restore_log` / `vp restore-log` restores an existing session's event table from a validated contiguous mirror, and `session.export` / `vp export` writes a bundle; `session.import` / `vp import` restores it as a **read-only archive** (preserved IDs/events/projections/approvals, no worktree, no agent runs); `session.rehydrate` / `vp rehydrate` explicitly recreates/attaches the session worktree, remaps imported agent task-worktrees by branch when possible, and returns the session to idle. `vp db-rebuild` can rebuild projects, policies, sessions, events, and covered projections from `projects.jsonl` plus per-session event mirrors; imported archives without `session.created` are skipped, and worktrees/artifact blobs must already exist. `plan_task_progress` is operational observation state, not a replay projection: replay/repair leaves it alone, and a daemon restart may lose the latest observation window. Do not claim full event sourcing or a complete archive rebuild (see AUDIT P1-5).
3. Do not add hidden model routing. Models and budgets are user-configured.
4. Do not add an agent write path outside its worktree. Shell runs under a macOS Seatbelt write sandbox (worktree + Git metadata + runtime scratch), with common credential/state read-denials, process-group cleanup, and a per-project policy that can only narrow access; projects can opt into a HOME read jail that denies HOME content except worktree/scratch/Git metadata/toolchains, or a broader user/volume read jail that also denies the home parent (normally `/Users`) and `/Volumes` outside those exceptions; system paths remain readable, and arbitrary reads outside the denied roots, network under `allow`, and daemon-mediated writes such as Docker volumes or GUI launch services are still not confined. Do not claim arbitrary shell is fully sandboxed; describe Verifier read-only as no write/edit tools plus a post-run tracked-file guard, not a full filesystem sandbox. External stdio ACP agents are launched through the same write sandbox with a scratch HOME, but their binaries are trusted user software and retain the policy's read/network access; remote Streamable HTTP/WebSocket ACP agents are trusted external services and are not locally sandboxed. Do not claim either ACP transport is credential- or network-isolated. Remote `remote_exec` runs on a configured SSH host under the remote user's authority, is not Seatbelt-confined, and is refused when the project policy requires `network=deny` or a read restriction the helper cannot enforce; remote writes are explicit, approval-classified, path-jailed operations, not local worktree writes.
5. Do not log API keys or full secrets. Keychain is for secrets.
6. Keep the JSON-RPC protocol backward compatible within major version 1.
7. Prefer deterministic Rust for scheduling/permissions/merge; LLM only inside a task.
8. The project org is four tiers: Leader → Manager → Worker → Labour. Worker/Labour slot scaling is deterministic, budget-gated, and hard-capped; Managers remain plan-owned and are never created or reassigned by the scaling controller.
9. One logical `gui` lease serializes browser and native computer surfaces; it is a single-daemon SQLite lease with TTL/heartbeat, persisted monotonic lease generation, post-action grace, a bounded FIFO wait queue, audit events, and operator release, not a distributed fencing token or cross-host queue. Helpers stay warm independently of lease ownership. Snapshot refs are bound to a snapshot generation and stale refs fail with `STALE_REF`; input actions are never auto-retried. Sensitive app/window targets require approval or are denied, and the `gui.action` timeline excludes screen content and typed text. Shell and worktree writes remain parallel, except cross-session Worker/Labour write scopes which wait on the global write-lease registry.
10. Aviiya is an external NovaBAIC resident agent. Do not implement a local Aviiya persona, memory, or chat runtime; only the bridge interface.

## Repo conventions

- Rust: `crates/vp-*`; no `unwrap()` in daemon library code unless clearly infallible. Prefer `anyhow::Result`.
- Swift: `apps/macos/VerlinPark/{App,Core,Features}`; UI state in `AppModel`, no business logic in views.
- Generated `apps/macos/VerlinPark.xcodeproj` and `apps/macos/build/` are gitignored; regenerate with XcodeGen.
- Do not commit local data, `target/`, DMGs, API keys, or daemon discovery files.
- New behavior needs a test or a reproducible scenario. New architectural decisions need an ADR.

## Security

The daemon is local-only: `127.0.0.1`, discovery token in a 0600 file. Do not bind to `0.0.0.0`. Do not add shell execution without the permission broker from M1. Treat repository/tool output as untrusted input.
